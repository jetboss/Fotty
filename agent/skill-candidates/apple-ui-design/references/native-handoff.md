# Native reference-to-build handoff

Use this for a substantive reference-driven implementation or comparison. It is
not a requirement to create screenshots or a new mockup for every small edit.

## Recover the approved contract

Identify the approved artifact and intended platform, window width, text size,
appearance and content state. Mark illustrative data and assets as illustrative.
Capture only the important relationships: first useful content, primary action,
artwork, navigation, alignment and density. A HTML mockup is not a native render;
its CSS, icons and fixed geometry are not a new product design system.

Preserve accepted product art, badge identity and navigation. Cover the whole
changed asset family and shared-component consumers. Do not use a preview
renderer’s icon restrictions as authority to replace the product’s artwork.

## Compare like with like

Use current native evidence for the same source/build and comparable conditions.
Keep separate:

- Missing or different content, actions and destinations.
- Unexpected placement, wrapping, artwork scale, density and hit-region overlap.
- Deliberate native or accessibility adaptations, with a reason.
- Untested behaviors: touch, focus, VoiceOver, keyboard and return navigation.

If only source or supplied layout observations exist, state that limit. A compile,
Catalyst render, old Mac binary or screenshot from another build cannot establish
current physical-phone interaction or complete visual fidelity.

For a narrow phone or accessibility text, preserve identity and meaningful text by
reflowing the group. Do not force the mockup’s column count through tiny text,
truncation or reduced hit regions. Check wide and narrow iPad windows only when
the changed composition affects them; readability can justify bounded columns.

## Close the actual handoff

Keep a small ledger: intended relationship, available evidence, observed
difference, adaptation or remaining defect. Make the next action specific:
for example, inspect the affected phone row at accessibility text, not “test UI.”

Report only the acceptance levels actually supported. If the requested mode is
discussion or audit, stop at findings. An implementation request authorizes its
scoped edits, not an unrelated redesign, installation or release. A discovered
functional defect is a separate finding, not permission to change data or media
ownership during visual polish.
